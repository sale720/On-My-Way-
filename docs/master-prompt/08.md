## 20. البنية التقنية والمعمارية

### 20.1 مرحلة فحص المشروع

قبل اختيار أو تغيير التقنية:

1. افحص ملفات المستودع.
2. حدد الإطار المستخدم.
3. افحص قاعدة البيانات الحالية.
4. راجع آلية المصادقة.
5. راجع النشر الحالي.
6. حدد الوظائف المكتملة والناقصة.
7. افحص الاختبارات.
8. حدد المخاطر والتعارضات.
9. قدم ملخصاً تقنياً وخطة تنفيذ.

إذا كان المستودع فارغاً، اقترح بنية مناسبة واشرح أسباب اختيارها.

### 20.2 معايير الاختيار التقني

اختر التقنيات بناءً على:

* نضج الأدوات.
* قابلية الصيانة.
* دعم اللغة العربية.
* أمان البيانات.
* قابلية التوسع.
* سهولة النشر السحابي أو داخل الجهة عند الحاجة.
* التكامل مع خدمات الخرائط والدفع.
* توافر المطورين.
* تكلفة التشغيل.

لا تفرض تقنية محددة إذا كانت التقنية الحالية مناسبة.

### 20.3 مبادئ التصميم

* افصل منطق الأعمال عن واجهة المستخدم.
* افصل محرك التغطية عن محرك الحجز.
* افصل التسعير عن الدفع.
* افصل الإشعارات عن منطق الحجز.
* استخدم واجهات API موثقة.
* استخدم معالجة موثوقة للأحداث المالية.
* اجعل العمليات القابلة للتكرار Idempotent.
* استخدم مهام خلفية للأعمال غير الفورية.
* استخدم Cache عند الحاجة، دون جعله مصدراً وحيداً للحقيقة.
* استخدم Feature Flags للميزات غير الجاهزة.
* وثّق قرارات المعمارية.

لا تبدأ بـ Microservices معقدة دون مبرر. يمكن استخدام Modular Monolith كبداية إذا كان مناسباً، مع فصل الوحدات منطقياً وإمكانية فصلها لاحقاً.

### 20.4 تكامل الخرائط

أنشئ Map Provider Adapter يتيح استبدال مزود الخرائط دون إعادة كتابة منطق التغطية والحجز.

قد يحتاج النظام إلى:

* Geocoding.
* Reverse Geocoding.
* Maps.
* Routing.
* ETA.
* Distance Matrix.
* Polygon/Point containment.
* إدارة حدود المناطق.

إذا كانت الخدمة الخارجية غير متاحة:

* استخدم واجهة Mock واضحة للاختبار فقط.
* لا تعرض نتائج الاختبار كأنها بيانات طريق حقيقية.
* وثّق متطلبات التفعيل.
* لا تجعل الاختبار المحلي يتطلب مفتاحاً سرياً حقيقياً دون ضرورة.

### 20.5 التكاملات الأخرى

جهز طبقات قابلة للتوسعة:

* مزود الدفع.
* SMS.
* البريد الإلكتروني.
* Push Notifications.
* خرائط وتوجيه.
* التحليلات.
* أنظمة المحاسبة.
* أنظمة ERP عند الحاجة.
* أدوات الدعم.
* الهوية الموحدة عند الحاجة.

لا تدّعِ وجود تكامل فعلي إلا بعد إتمامه واختباره.

## 22. الأمن والامتثال

صمم النظام مع مراعاة الأنظمة السعودية المنطبقة على نشاط المنصة، بما في ذلك متطلبات حماية البيانات الشخصية والتجارة الإلكترونية والمدفوعات والفوترة بحسب طبيعة النشاط ونموذج التشغيل.

لا تفترض انطباق كل متطلب على كل نموذج دون تقييم قانوني مناسب.

المتطلبات التقنية:

* HTTPS.
* إدارة آمنة للجلسات.
* تخزين كلمات المرور باستخدام خوارزميات مناسبة.
* حماية من CSRF وXSS وSQL Injection.
* التحقق من المدخلات.
* Rate Limiting.
* حماية من إساءة استخدام رموز OTP.
* إدارة أسرار آمنة.
* تشفير البيانات الحساسة عند الحاجة.
* صلاحيات دقيقة.
* سجل تدقيق.
* إدارة الجلسات والأجهزة.
* النسخ الاحتياطي.
* خطة استعادة.
* مراقبة الأخطاء.
* إخفاء الأسرار والبيانات الحساسة في السجلات.
* اختبار صلاحيات الوصول إلى الموارد.

ضع تصميماً واضحاً للخصوصية، والاحتفاظ بالبيانات، والموافقة، والتصحيح، والحذف، والتعامل مع الحوادث الأمنية، وفق المتطلبات التي تنطبق على المنتج فعلياً.

لا تستخدم بيانات حقيقية لعميلات أو مقدمات خدمة في الاختبارات العامة.
